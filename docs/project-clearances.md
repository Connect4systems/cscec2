# دورة بنود المشروع والمستخلصات

## التسلسل

1. تجهيز البنود والكميات في Tender Analysis ثم إنشاء Contractual Clauses.
2. إعداد Costing Notes وBOQ واعتماد التسعير، ثم إنشاء Project Offer.
3. اعتماد العرض وإنشاء Project Contract؛ تنتقل البنود والضرائب والاستقطاعات، ويمكن تعديل المستندات المسودة.
4. اعتماد العقد ينشئ Project باسم المشروع المدخل. المشروع يحتفظ بمراجع العقد والعرض والتحليل وبنود العقد دون عرض الأسعار.
5. من قائمة Create في المشروع، اختيار Project Clearnce لمستخلص العميل، أو Subcontract Clearnce لمستخلص مقاول الباطن واختيار المورد.
6. إدخال كمية الفترة الحالية لكل بند، ومراجعة الضرائب والاستقطاعات، ثم الاعتماد. الاعتماد ينشئ الفاتورة والقيد ويحدث كميات المشروع داخل المعاملة نفسها؛ أي فشل يمنع إكمال الاعتماد.

## الجدولان في المشروع

- Project Clauses: تفاصيل البنود، الكمية التعاقدية، المنفذ والمتبقي ونسبة الإنجاز للعميل ولمقاولي الباطن كل على حدة.
- Clause Groups and Progress: ملخص المجموعات حسب وحدة القياس؛ لا تُجمع الأمتار مع الأمتار المكعبة مثلاً.

الجدولان للقراءة فقط. صفوف المجموعات عناوين، ولا تمثل كمية قابلة للصرف. الملخص يجمع بنود التفاصيل. حقول Rate وAmount غير موجودة في واجهة جدول المشروع، ولا تُنسخ أسعار جديدة إليه. الأعمدة القديمة في قاعدة البيانات لا تُحذف.

منفذ العميل مستقل عن منفذ مقاول الباطن؛ لا يتم جمعهما باعتبارهما تنفيذًا إضافيًا لنفس الكمية. المسودات والملغيات لا تدخل في المنفذ. إلغاء مستخلص يعيد احتساب الكميات من بقية المستخلصات المعتمدة.

## مستخلص العميل

السعر يأتي من Project Contract. المستخدم يدخل كمية الفترة الحالية أو نسبتها من الكمية المتبقية، وتظهر كمية العقد والسابق والحالي والمتبقي. لا يسمح بتجاوز كمية العقد. الضرائب والاستقطاعات تأتي من العقد ويمكن تعديلها في المسودة. الضرائب الثابتة من نوع Actual تبدأ بصفر لتحديد نصيب الفترة، فلا تتكرر القيمة الثابتة الكاملة مع كل مستخلص.

## مستخلص مقاول الباطن

يستخدم البنود نفسها ويستبدل العميل بالمورد. يدخل المستخدم سعر مقاول الباطن ويختار قوالب ضرائب وخصومات المشتريات عند الحاجة. السابق الخاص بالمورد يظهر منفصلًا، لكن حد الكمية المتاحة يعتمد على إجمالي مستخلصات جميع الموردين للبند. بذلك لا يمكن صرف كامل الكمية لأكثر من مقاول. الأسعار الصفرية مسموحة أثناء التجهيز، ويلزم سعر موجب للبند ذي الكمية الحالية عند الاعتماد.

المستخلص مرتبط بالمشروع وبنود عقد المشروع؛ هذه الدورة لا تنشئ عقد مقاول باطن مستقلًا ولا تعتمد على Purchase Order مخصص.

## القيد والفاتورة

الاعتماد ينشئ ويعتمد Sales Invoice للعميل أو Purchase Invoice للمورد، ببند خدمي غير مخزني واحد اسمه **بنود اعمال**، كميته 1 وقيمته صافي الأعمال بعد الخصم وقبل الضرائب. تنتقل مبالغ الضرائب المحسوبة إلى الفاتورة، ويجب أن يتطابق إجماليها مع المستخلص.

الفاتورة تنشئ القيد الأساسي للإيراد أو المصروف عبر ERPNext. إذا وجدت استقطاعات، ينشأ Journal Entry مستقل لتسويتها مع حساب العميل أو المورد، دون إثبات الإيراد أو المصروف مرة أخرى:

- العميل: مدين حسابات الاستقطاعات، دائن حساب العميل.
- المورد: مدين حساب المورد، دائن حسابات الاستقطاعات.

مثال دون ضرائب: أعمال 100 واستقطاع 10 تعطي فاتورة 100 وقيد استقطاع 10 ورصيدًا مستحقًا 90. لا ينشأ قيد استقطاع عند عدم وجود استقطاعات. السداد الفعلي يتم عبر Payment Entry القياسي. أزرار Open Invoice وDeduction Entry تفتح المستندات الناتجة.

يلزم ضبط حسابات العميل/المورد وحساب الإيراد/المصروف الافتراضي ومركز التكلفة للشركة، وحساب فروق التقريب عند الحاجة. المستخدم يحتاج صلاحيات إنشاء واعتماد المستندات المحاسبية وصنف الأعمال إذا لم يكن موجودًا.

إلغاء المستخلص يلغي قيد الاستقطاعات ثم الفاتورة ويعيد احتساب كميات المشروع. قيود ERPNext القياسية تمنع الإلغاء إذا كانت الفاتورة مرتبطة بسداد أو مستند لاحق يمنع الإلغاء؛ يجب معالجة تلك الروابط أولًا.

## حفظ التاريخ وإعادة الشراء للوضع القياسي

الترحيل يعيد تسمية DocType الفعلي Clearence إلى Project Clearnce، وPurchase Clearence إلى Subcontract Clearnce. يحتفظ بالمستندات والأسماء والروابط والجداول القديمة، ويضع علامة Legacy Record على المستندات القديمة. لا يُنشئ لها فواتير أو قيودًا جديدة بأثر رجعي، ولا يحول بنود Item القديمة تلقائيًا إلى Contractual Clauses؛ لذلك لا تدخل كمياتها في مؤشرات الدورة الجديدة دون تسوية منفصلة.

إذا وجد الاسمان القديم والجديد معًا، يتوقف الترحيل قبل إعادة التسمية ويطلب معالجة التعارض؛ لا يتم دمج بيانات متعارضة تلقائيًا. إعادة تسمية DocType تتضمن تغييرات بنيوية قد تثبتها Frappe أثناء العملية.

أزيلت ملفات تخصيص المشتريات المصدرة وربط JavaScript وoverride الخاصة بـPurchase Order وPurchase Invoice. الترحيل يعيد تحميل تعريفات ERPNext ويزيل Property Setters المشحونة مع التطبيق ويخفي حقول المقاولات القديمة مع حفظ بياناتها. لا يحذف Client Scripts أو تخصيصات أخرى أضافها مدير الموقع خارج التطبيق.

## النشر والتحقق

نفذ أولًا على **نسخة تجريبية من الموقع وقاعدة البيانات** مع نسخة احتياطية. افحص مستخلصًا قديمًا، ثم أنشئ دورة جديدة تشمل مستخلص عميل ومقاول باطن واعتماد كل منهما وإلغاءه. تحقق من دفتر الأستاذ ورصيد الفاتورة والكميات قبل نشر الإنتاج. الاختبارات المحلية لا تعوض هذا التحقق.

```bash
cd ~/frappe-bench
bench --site TEST_SITE backup --with-files
bench --site TEST_SITE migrate
bench build --app contractor
bench --site TEST_SITE clear-cache
bench restart
bench --site TEST_SITE run-tests --module contractor.contractor_app.doctype.project_clearnce.test_accounting_native
```

استبدل TEST_SITE باسم النسخة التجريبية. اختبارات المحاسبة تحتاج شركة تجريبية ذات حسابات افتراضية وإعدادات محاسبية مكتملة، وتشغل فواتير وقيود ERPNext الفعلية داخل معاملات الاختبار. لا تُشغل اختبارات المحاسبة على الإنتاج.

يمكن مراجعة الروابط والكميات والفواتير والقيود لمشروع محدد دون تعديلها:

```bash
bench --site TEST_SITE execute contractor.contracting_audit.check --kwargs '{"project":"PROJ-0001"}'
```

التقرير يتحقق من حدود الكميات، ووجود فاتورة معتمدة ببند أعمال واحد، وتطابق الإجمالي، وعدم مشاركة الفاتورة بين مستخلصين، ووجود قيد استقطاعات معتمد ومتوازن. لا يغني عن مراجعة حسابات الأستاذ أو اختبار دورة العمل على بيانات الموقع.
